## Review of CR-158 — the extension directory form

**What I checked.** `read_extension_manifest` and its two new helpers in `src/agentmarshal/journal/extensions.py:460-640`, the archived change under `openspec/changes/archive/2026-10-03-extension-directory-form/`, the landed `openspec/specs/extension-manifest/spec.md`, the 23 delta scenarios against test docstrings, and the three callers (`brief.py:232`, `review.py:1071`/`:1247`, `gate.py:820`).

**Acceptance, criterion by criterion:**

- *Both candidate paths, both-forms refusal, schema-2 requirement* — `_manifest_candidate` is called once per form (`extensions.py:601-606`); both resolving raises naming both paths (`:607-611`); neither is `ExtensionManifestMissing` naming the file-form path (`:613-616`); a directory-form schema 1 is refused with "the directory form requires a manifest of schema 2" (`:625-629`).
- *Named paths must be regular files inside the directory* — `_require_existing_directory_file` (`:525-561`) walks every component from the named path up to the extension directory refusing a lexical symlink first (so dangling `bin/`→nowhere is a link refusal, not "missing"), then strict-resolves, then compares `resolved != target`, then requires `is_file()`. `..` is already impossible: `validate_scope_entry` rejects `.`/`..` components (`contracts.py:126-131`) and `_require_directory_file` additionally pins `parts[0]` to `bin`/`lock`. The single-file counterpart refusal is at `:634-639`, and design.md states the rationale.
- *Symlink refusals extended, directory exposed* — the lexical pre-existence link check now covers `<name>/` as well as the manifest file (`:485-493`); `directory` is a frozen-dataclass field with a trailing default (`:101`) filled only by the filesystem reader via `replace` (`:633`), so `parse_extension_manifest_text` leaves it `None`.
- *Callers and fixtures unchanged* — all three callers read only `.documents`/`.footprint`; nothing compares `ExtensionManifest` instances for equality, so the new field is inert for the gate, and no fixture changed. The embedded gate's `_manifest_from_tree` and `_extension_name_from_path` are untouched, which is the stated non-goal.
- *Change artifacts* — proposal, design, tasks and a delta with the MODIFIED header matching `spec.md:15` byte for byte; archived, and each of the four new requirements appears exactly once in the capability spec. All 23 delta scenarios have a test whose docstring names them.

**One advisory finding.** The new spec text asserts more than the reader does about symlinks above the extension: `openspec/specs/extension-manifest/spec.md:218-222` says "a symlink in any component of the path SHALL each be refused as a link — dangling or not, and before existence is decided", but the lexical pre-existence check in `extensions.py:486-493` stops at `.agentmarshal/extensions` (`while component != extensions_dir`), and components at or above that are caught only by `resolved != path` after strict resolution. A *dangling* symlink at `.agentmarshal/extensions` or at `.agentmarshal` therefore makes `path.resolve(strict=True)` raise `FileNotFoundError`, both candidates return `None`, and the reader reports `ExtensionManifestMissing` instead of refusing a link. The behaviour itself is the pre-existing file-form behaviour and carries no read-through hazard — nothing can be read through a dangling link, and the gate still fails the check for a named extension — but design.md's narrower claim ("a symlinked extensions directory — is caught by strict resolution landing elsewhere") is the accurate one, and the requirement's "any component … dangling or not" overstates it. Either narrow the requirement to the components the reader checks lexically, or move the loop's boundary to the project root.
