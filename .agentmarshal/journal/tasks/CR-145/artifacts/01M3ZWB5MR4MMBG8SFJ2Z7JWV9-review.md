Проверил контракт, delta spec, архив изменения и полный новый код `records.py` против снапшота. Главное сошлось: registry `_RULES` + таблица `_RULE_FROM_SCHEMA` зарегистрированы в точном порядке сегодняшних проверок (schema → record-type → predicate → reviewed-contract → fields → … → provenance → recorded-by → finding-binding → placement), проверка версии схемы вынесена явным первым шагом вне registry, сторона валидации — один параметр `for_write`, и набор правил на write-пути остался ровно тем же (контекст-зависимые правила, чьё placement вызывающий не даёт, пропускаются — поэтому `validate_record_content` не начал проверять task, а `validate_record_for_write` — filename). Read-путь стал строгим подмножеством прежнего, так что новых отказов на чтении появиться не может — это и есть гарантия для `agentmarshal validate` и для журналов прошлых релизов. - `advisory-rule-granularity`: в `src/agentmarshal/journal/records.py:559` таблица держит по одной записи на проверку целого типа записи — правило `review` (строка 357) покрывает ~20 отдельных проверок полей и значений внутри `_validate_review_record` (vocabulary вердикта, форма `reviewer`, уникальность findings, …), то же для `acceptance`, `finding`, `provenance`, `completed`; критерий просит отображать «each check … on a field or a field's value», и завтрашняя проверка, добавленная внутрь `_validate_review_record`, не получит записи в таблице и не будет поймана completeness-тестом — ровно тот режим отказа, против которого ADR-0015 решение 7 и задумано.
