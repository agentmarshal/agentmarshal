Now the findings.

**gate-admits-forged-low-schema-record** — `design.md`'s Risks section justifies the read-time loosening with "the journal is append-only so it cannot appear in a real journal." That premise is false for the one call site the contract names: `gate.py:1070` runs `validate_record_content` over **added** records at the merge boundary, and append-only only prevents modifying records that already exist — it does nothing about a newly added forged one. Concretely, a candidate that adds `…/records/01J…-session.json` with `{"schema": 3, …, "activity": "coordination"}` was refused by the gate before this change ("session activity 'coordination' requires schema 6") and is now accepted, because `coordination` is bound to 6 and 6 > 3 so `_validate_record` skips it (`records.py:528-532`). The record then lives in the journal, where a pinned earlier reader refuses it as a malformed field rather than as an unsupported schema — the exact outcome `openspec/specs/session-activity/spec.md:28` ("An older reader refuses a coordination session by its schema") exists to prevent. The same holds for an added `completed` record stamped 3 carrying `completed_finding`, and for a `finding` record stamped 3. The behaviour itself is what criterion 3 mandates, so I am not blocking on it; what needs fixing is the recorded reason, since an operator accepting this risk is accepting it on a statement that does not hold.

**session-writer-not-derived-from-its-record** — `create_session_record` (`records.py:1144`) is the one writer whose stamp is not derived from the record it builds: it calls `session_record_schema(activity)`, which derives from the synthetic two-key dict `{"record_type": "session", "activity": activity}` (`records.py:1118`). The numbers are right today, but the task's stated objective is to lay ground so a later schema "only registers its fields and rules" — when ADR-0022 adds a schema-7 session field, every other writer picks the stamp up from `_minimum_schema(record)` automatically while this one keeps returning 3 or 6, silently writing a record that under-declares its schema.

**minimum-schema-assigns-instead-of-max** — `records.py:986`: the finding branch does `schema = 4` where the two branches below it correctly do `max(schema, …)`. Harmless while `_BASELINE_SCHEMA` is 3, but this is code written explicitly for the next schema to extend: if ADR-0022's record model raises `_BASELINE_SCHEMA`, a finding record would be stamped *down* to 4 while carrying baseline fields a later schema introduced.
