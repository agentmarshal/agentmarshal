I reviewed the diff against the contract, the process-log spec, ADR-0014 decisions 9 and 13, and the surrounding code (`steps.py`, `status_view.py`, `cli.py:_run_status`, `localstate.py`, `process_log.py`, `display.py`).

**What holds up.** All five acceptance criteria are met. `open_steps` implements criterion 2's rule exactly — the per-step `step-ended` event, the activity→record mapping (implementation→implementation session, review→review record, everything else→session of that activity), strictly-after comparison in UTC, injectable `now`, and the documented degradations (unreadable `created_at` never closes; unreadable `at` orders at the start of time; a `step-started` missing step/activity/deadline reads as no step). Every scenario in the delta spec has a test whose docstring names it, including the two "one computation" and sidecar ones, and the delta is archived with `openspec/specs/process-log/spec.md` carrying the identical ADDED headers. Both byte-exact pins (`test_status_view.py:250`, `test_display.py:211`) gained only the `Paths:` line, and `test_status_writes_nothing_into_the_local_state` pins the read-only promise — `read_events` only checks `is_dir()`, so `status` still creates nothing. Escaping is applied to the whole composed line in both new renderers, and a tab is category `Cc`, so the list's new fourth field cannot be forged from a contract title.

Four non-blocking observations follow.

A `completed` (or `abandoned`) record does not close a step: `_closes_step` in `src/agentmarshal/steps.py:536` matches only `review` and `session` records, so a task finished without a trailing session of the step's activity keeps printing `Overdue step …` from `status CR-001` and keeps the `overdue-step` mark in the list forever. ADR-0014 decision 9 enumerates the closing records as "an implementer session, a review, `completed`" (`docs/adr/ADR-0014-where-things-live.md:112`); the contract's criterion 2 enumerates only the first two, which is what was built, so this is a gap between the contract and the ADR rather than a deviation from the contract.

The paths line is space-delimited, so its three fields stop being separable once a path contains a space: `print_paths_line` in `src/agentmarshal/journal/status_view.py:208` joins `journal=`, `process-log=` and `local-state=` with single spaces, and `escape_for_display` leaves `Zs` alone (`_FORGEABLE_CATEGORIES` is `Cc`, `Cs`, `Zl`, `Zp` plus the bidi controls, `src/agentmarshal/journal/records.py:938`). A clone under `/home/u/my repo` prints `journal=/home/u/my repo/.agentmarshal/journal process-log=…`, which no reader can split; the rest of `status`'s stdout uses tabs for exactly this reason.

`status` now parses the entire process-log directory on every invocation and rescans it once per task: `cli.py:981` calls `read_events(state)` before either branch, and the list loop at `cli.py:988` calls `open_steps` per task, each call walking all events twice. The log directory is bounded at 50 MB (`DIRECTORY_CAP_BYTES`), i.e. on the order of 200k JSON lines, so a busy clone with a few dozen tasks pays a full re-parse plus O(tasks × events) scanning on a command that was previously a pure journal read; grouping events by task in one pass, and passing only the one task's events in the detail form, would keep it O(events).

The documentation of `status`'s output is now contradicted and could not be fixed here, since `docs/` is outside the contract scope: `docs/quickstart.md:477` promises that `status`'s stdout "stays exactly as anything parsing it expects" (the stated reason `Placement:` goes to stderr), `docs/sidecar.md:401` records `status`'s "stdout unchanged", and the sidecar transcript at `docs/sidecar.md:306` shows the detail output without the new first line. The contract itself implies stdout ("existing status tests change only by that line", and those pins are stdout pins), so the stream choice is the contract's; only the docs need a follow-up.
