Findings follow.

**CR-097-F1** — `src/agentmarshal/journal/review.py`, in `dry_run_review`: the comment above the `rev-parse --verify HEAD^{commit}` probe says "the caller is told which of the two it got", but nothing tells them. `dry_run_review` returns `None`, prints nothing, and `_run_review` in `src/agentmarshal/cli.py` prints one constant line — `"dry run: reviewer output has a parseable verdict; nothing was recorded"` — on every success. In a repository with no commit the command runs in an empty `snapshot.mkdir()` directory and the operator is told the same thing as a run in a populated snapshot, while `docs/quickstart.md` (added by this same change) tells them it ran "in a snapshot of `HEAD`". `test_dry_run_works_in_a_repository_with_no_commit` asserts only `"parseable verdict" in out`, which confirms no distinguishing signal exists. The design note's own justification for departing to a HEAD snapshot is that an empty directory misleads for exactly the configuration proposal 015 reports; the fallback silently reinstates that, and the new documentation now overstates it.

**CR-097-A1** — `src/agentmarshal/journal/review.py`, `_reject`/`_parse_verdict`: the `preserve_output` keyword is inert. It was threaded through `_reject` and all ten `reject(...)` sites so the dry run could suppress preservation, but `dry_run_review` immediately calls `_preserve_output(output)` itself in its `except ReviewLaunchError` handler. Exactly one file is written either way; the only observable difference is message wording. The flag and the closure can be dropped and `dry_run_review` can prefix the message from an ordinary `_parse_verdict(output)`. Separately, the file the dry run leaves still carries the `agentmarshal-rejected-verdict-` prefix, though a dry run rejects no verdict.

**CR-097-A2** — `src/agentmarshal/cli.py:153-166`: `--task`, `--commit`, `--base`, `--role`, `--vendor`, `--model`, `--email` all lost `required=True` and the mutually exclusive group lost `required=True`, but their `help=` strings are unchanged. `agentmarshal review --help` now presents every flag of the recorded path as optional, so the requirement is discoverable only by running the command and reading the exit-1 message — in a change whose stated purpose is that the command's contract be readable where it is configured. The exit code for a missing flag also moves from argparse's `SystemExit(2)` to a returned `1`, which a caller distinguishing usage errors from operation failures will see; no test pins either behaviour.

**CR-097-A3** — `src/agentmarshal/journal/review.py`, `dry_run_review`: the "needs `--model`" guard is `"{model}" in template` against the raw environment string. A template written as `{model!r}` or `{model:>8}` — both of which `_reviewer_command` substitutes happily — skips the guard, and the command is then launched with an empty model instead of being refused. The scan you already wrote, `_unsupported_placeholder`, walks real format fields and could answer this question exactly.

**CR-097-A4** — `openspec/changes/archive/2026-09-17-document-the-reviewer-contract/specs/reviewer-adapter/spec.md` and `openspec/specs/reviewer-adapter/spec.md`: the contract's first acceptance criterion exempts "the two documentation scenarios", and `tasks.md` splits the documentation work into 1.1 and 1.2, but the spec carries a single documentation scenario folding both obligations into one `THEN`. Substantively the documentation covers both halves; the count in the criterion and the count in the delivered spec do not agree, and one of the two should move.
