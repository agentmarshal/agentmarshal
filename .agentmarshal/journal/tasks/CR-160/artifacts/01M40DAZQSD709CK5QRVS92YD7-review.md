**`coordination-schema-requirement-left-untrue`** — `openspec/specs/session-activity/spec.md:28-38` (and the identical block in `openspec/changes/archive/2026-10-03-session-fields-schema-7/specs/session-activity/spec.md`): the MODIFIED requirement "An older reader refuses a coordination session by its schema" was amended only on its *second* clause. It still says a session whose activity is `coordination` "SHALL carry the schema number that introduced the value" (6), and its scenario "coordination stamps the newer schema" still has the unqualified `WHEN a session is recorded with the activity coordination → THEN the record carries the newer schema number`. But `_minimum_schema` (`src/agentmarshal/journal/records.py:1242`) takes `max(6, 7)` for a coordination session carrying a family field, and the change's own test asserts exactly that — `tests/test_record_schema.py:375-390` stamps **7** for `activity="coordination", fallback_reason="fell back"`. The new requirement at `openspec/specs/session-activity/spec.md:91-97` says so too ("A session record carrying any of … SHALL carry schema 7"), so the published capability now contradicts itself. The "unless a field of the schema-7 session family raises it to 7" escape was attached to the other-activity clause only; the coordination clause and its scenario need the same qualifier (the parallel "other activities keep their schema" scenario *was* qualified at line 41-42). The acceptance criterion requires every published requirement this change makes untrue to be modified by this change, with the exact header kept — so the fix belongs in both the archived delta and the published spec.

**`commit-not-registered-in-forgeable-text-table`** (advisory) — `src/agentmarshal/journal/records.py:305-311`: the contract's acceptance says "each string field passes the forgeable-text rule registered for exactly that record type and field", and ADR-0022 section 8 says "every displayed string the new fields introduce follows the same pair". `commit` is a displayed string and gets no `_FORGEABLE_TEXT_FIELDS` entry; only the other four do. The reasoning in `design.md` is sound and the behaviour is equivalent — `session-fields-7` runs at rule index 536, ahead of `forgeable-text` at 680, and its 40-lowercase-hex `fullmatch` admits no character `_reject_control_characters` refuses, so the registration could never fire — and the change's own new requirement narrows the published wording to the four fields. It is nonetheless a deviation from the contract's literal acceptance text, decided unilaterally rather than through a contract amendment, and worth the operator's explicit blessing.
