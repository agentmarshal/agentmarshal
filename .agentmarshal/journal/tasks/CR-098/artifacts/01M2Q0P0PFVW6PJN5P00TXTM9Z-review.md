Review of `35e75be07ca73b71b55d55ba37ae8556a81388ac` against CR-098.

**template-gate-never-evaluates** — `templates/github/agentmarshal-governance.yml:74` decides whether to run the gate by greping *the committed tree at* `$HEAD_SHA` for a record naming that same SHA. A commit's own tree cannot contain its own hash, so that condition is never true: the `agentmarshal gate` invocation on lines 76–79 is unreachable and the shipped gate job is now green-by-construction on every pull request. It is also the wrong place to look for the intended future case: the gate reads review records from the working-tree journal (`src/agentmarshal/journal/gate.py:583`, `load_task_status`), and Phase C materialisation (`docs/github-enforcement.md:48-57`) writes the record into the checkout rather than committing it — so even after materialisation lands, `git grep <rev>` would not see it. The spec's second scenario, "a head that carries its review is gated", cannot be exercised.

**deterministic-lane-no-longer-gated** — the same block skips the *entire* gate, not just the review-bound lane. `openspec/specs/trust-preconditions/spec.md` requires it to "succeed **without evaluating the review-bound lane**", and `run_gate` enforces much more than review: scope against the merge-base contract, append-only evidence, base-state/lifecycle, record-path collisions, attestation, and the journal-only deterministic lane that needs no review at all (`gate.py:655-732`). Opening and completion branches — which `docs/self-hosting-workflow.md:115-117` says take the deterministic lane — carry no review record for their head SHA either, so they now fall into "judged nothing" and are not gated at all. The newly documented `CR-<number>` branch-naming requirement is likewise no longer enforced, since `task` is only consumed on the dead branch. This is a strictly larger loss of enforcement than the `continue-on-error` it replaced.

**ci-check-github-only** — `src/agentmarshal/doctor.py:152` looks for a CI definition only under `.github/workflows`. AgentMarshal is explicitly vendor-neutral (`README.md:3`, `docs/overview.md:18`) and this repository's own CI is `gitflic-ci.yaml` at the root, which runs `uv run agentmarshal validate` on line 23. A GitFlic or self-hosted adopter therefore gets a permanent `FAIL: CI validate definition` with correct CI in place — the "check that is red by construction" that this change's own spec Purpose forbids. `design.md` states the check as "whether a CI definition invoking `validate` exists" with no provider restriction and records no departure, so acceptance criterion 1's "follows design.md's decisions or records why it departed" is unmet here.

**actor-check-ignores-actors-table** — `src/agentmarshal/doctor.py:115-124` reports, whenever `AGENTMARSHAL_ACTOR` is unset, that "records will resolve to the invoking git identity". `resolve_recorded_by` (`src/agentmarshal/journal/actors.py:84-104`) resolves override → **project actors table** → git identity, so a project that has configured `actors` in `.agentmarshal/project.json` — the documented ADR-0006 mechanism — attributes agents correctly with the variable unset, and is told otherwise. That project is permanently red for a condition it has met. `src/agentmarshal/project.py` is in scope and untouched; consulting the table is what would make this report true.

**enforcement-doc-now-false** — `docs/github-enforcement.md:30` still tells operators the gate check is "shipped **advisory** (`continue-on-error: true`)", and lines 60-65 still promise that it "fully enforces the journal-only lanes (openings and completions), and the **scope**, **append-only**, **base-state** and **lifecycle** checks on every candidate". Both statements are false as of this commit. The file is outside the contract's scope, so this is flagged rather than expected in this change, but the shipped docs now contradict the shipped template.

**precondition-names-duplicated-in-cli** — `src/agentmarshal/cli.py:73-75` re-states the three check names as string literals to classify them at `cli.py:395`. Renaming a `DoctorCheck` in `doctor.py:192-200` silently reverts those checks to gating, with no test pinning the two lists together; a flag on `DoctorCheck` would carry the fact where it is defined. Relatedly, `run_doctor`'s blanket `except Exception` means an unexpected crash inside a precondition check is also classified as merely "unmet" and exits 0.

**summary-wording-softens-real-failures** — `cli.py:393` now prints "N check(s) reported unmet" for *all* failures, including hard ones like a missing git executable or an unparseable `project.json` (see the updated expectation in `tests/test_doctor.py`, decode-error case). The criterion only required that the summary stop claiming all checks passed; describing a broken project as "unmet" understates it.

What holds up: `init`'s checklist is printed once with the cost of skipping each item and configures nothing (`cli.py:347-364`); the reviewer-command check never echoes the command and the secret-leak test covers it; the exit-status rule is implemented correctly; every non-template scenario has a test whose docstring names it; `continue-on-error` is gone and `tasks.md` is ticked.
