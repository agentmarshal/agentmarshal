Now the advisory findings.

**`mnemonic-prefix-test-is-vacuous`** — `tests/test_review_launcher.py:2558` (`test_the_named_files_are_not_bent_by_diff_prefix_config`) sets `diff.mnemonicPrefix` and then asserts `"c/blob.bin" not in captured.err`. git does not apply mnemonic prefixes to a commit-to-commit diff: the `diff.mnemonicPrefix` documentation enumerates the comparisons it affects (`git diff` index-vs-worktree, `git diff HEAD`, `--cached`, `HEAD:file1 file2`, `--no-index`), and `git diff A..B` is not among them — `builtin_diff_tree` never calls `diff_set_mnemonic_prefix`. So this test passes identically with the pinned `--src-prefix`/`--dst-prefix` flags removed, and tasks.md 5.2's "verify: a launcher test under `diff.mnemonicPrefix` names the file plainly" does not actually verify the pinning. `diff.dstPrefix` (git 2.41+) is the knob that really bends `_diff_path`'s `b/` strip; `diff.noprefix` is the other. The same inaccurate claim appears in `design.md`'s first decision and in the code comment at `src/agentmarshal/journal/review.py:1171-1172`, both inherited from `gate.py:551`'s `leak_scan_diff` docstring. The pinning itself is right and worth keeping — only the stated justification and the test that is supposed to pin it are wrong. (I could not run git here to confirm empirically; this rests on the config documentation and git's source layout.)

**`review-diff-not-pinned-against-diff-drivers`** — `src/agentmarshal/journal/review.py:1178-1189` pins the two prefix flags but omits `--no-textconv` and `--no-ext-diff`, which `leak_scan_diff` (`gate.py:560-571`) pins for the explicit reason that they "stop the repo's own diff drivers from rewriting or redacting what the scanner sees, which could hide a secret". design.md's first decision enumerates precisely how `review` departs from `leak_scan_diff` — it argues the `--text` omission at length — and is silent on these two, so the departure is undocumented rather than decided. The consequence is that of the two diffs this codebase derives from the same merge base, the one a human review attests is the one a configured `textconv` attribute or `diff.external` driver can rewrite. That needs repository config, which a candidate commit cannot supply, so it is an operator foot-gun rather than a candidate-controlled bypass — hence advisory, not blocking.

**`launcher-imports-merge-gate-for-marker-config`** — `src/agentmarshal/journal/review.py:38-42` makes the review launcher depend on the merge gate for two small config readers and forces it to catch and translate `GateError`. `markers_from_config` is a thin composition of `read_project_file` + `private_markers_from_project`, both already reachable from `review` via `project`/`capture`, and `capture.py` is where the rest of this marker vocabulary lives (`safe_path`, `render_undecodable_files`, `private_markers_from_project`). Moving the pair down to `capture.py` (or `project.py`) would give both callers the same source without pointing the launcher at the gate. Structural only; nothing is wrong at runtime.

One behavior worth flagging without calling it a finding: when a diff has undecodable files and the merge-base `project.json` cannot be read, `review` now refuses the whole review (`review.py:1206-1209`) where the gate degrades to a warning. design.md argues this explicitly ("naming is required, so 'cannot read the marker config' is the honest out"), so it is a recorded decision — but masking with built-in signature patterns and an empty marker tuple would have been strictly more available than refusing, and that alternative is not weighed.
