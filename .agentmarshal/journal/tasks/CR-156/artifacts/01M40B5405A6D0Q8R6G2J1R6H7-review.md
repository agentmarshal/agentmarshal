Что сошлось по всем пяти acceptance:

- Change `outbox-send-and-status` лежит в `openspec/changes/archive/2026-10-03-outbox-send-and-status/` с `proposal.md`, `design.md`, `tasks.md` и дельтой; `openspec/changes/` больше ничего не держит. Заголовок MODIFIED-требования (`### Requirement: \`outbox check\` scans what would be sent and refuses by exit status`) совпадает байт-в-байт с тем, что положила CR-150, два ADDED — новые; в `openspec/specs/outbox/spec.md` каждое из пяти требований и все 43 сценария встречаются ровно один раз. Все 43 сценария дельты покрыты тестом, чей docstring их называет (plus sha256-вариант restore-теста).
- `send`: `_run_check` запускается первым и любой non-zero отказывает (`outbox.py:659`); отказ при чём-либо staged вне `.agentmarshal/upstream/` (`outbox.py:688`), причём оба конца rename учтены; `git add --force -- .agentmarshal/upstream` и ровно один `git commit --message` с перечислением файлов, затем печать `rev-parse HEAD`. Сети нет — только `subprocess` с `git`. Restore через `update-index --index-info` + `--force-remove` действительно не пишет object id, работает при unborn HEAD и трогает только пути под outbox; `committed`-флаг не даёт откатить сделанный commit.
- `status --index`: sha256 файла как он есть, lowercase hex; обе формы `Source:`; entry идентифицируется digest'ом, строки сохранены; нерегулярный/нечитаемый файл — non-zero; отсутствующий index и отсутствующий outbox — отказ с сообщением; сети нет.
- Не-UTF-8 имена: `_shown_name` (`outbox.py:182`) через `os.fsencode` + `backslashreplace`, и именно escaped-форма идёт и в `safe_path`, и в name-scan — значит marker в таком имени всё ещё маскируется, а сам name-hit всё ещё отказывает check'у. `cli.py` не тронут, hook на месте.

Три замечания, ни одно не блокирующее.

`send-rename-branch-untested` — в `tests/test_outbox.py:673` сценарий «staged outside the outbox» проверяется только добавленным файлом (`status` = `A`), а ветка `_staged_paths` для rename/copy (`src/agentmarshal/outbox.py:548`, три токена вместо двух, оба пути в набор) и оба её `_OutboxGitError`-guard'а не исполняются ни одним тестом в репозитории — `git mv` в тестах не встречается вообще. Разбор по моему чтению верен (`--name-status -z` даёт `R100\0src\0dst\0`), но `tasks.md` 2.2 утверждает «both halves of a staged rename counted — verify: the test named after the scenario», и этой проверки нет: регрессия в счётчике токенов разъехала бы парсинг молча.

`checked-blob-pin-taken-after-the-check` — требование говорит «the command SHALL verify the staged blobs are the files the check vetted», но `expected` считается в `src/agentmarshal/outbox.py:709` уже после того, как `_run_check` закончил читать файлы: pin фиксирует содержимое на момент `hash-object`, а не на момент проверки. Правка черновика в окне между чтением check'а и `_checked_blob_ids` (несколько subprocess-вызовов: `_locate`, `_markers`, `iterdir`, `diff --cached`, `ls-files`) проходит mismatch-сравнение и коммитится как «проверенная», при нулевом exit. Окно узкое и требует параллельного писателя, а `design.md` этот механизм описывает честно («before the add the command pins…»), поэтому advisory — но гарантия слабее, чем формулировка SHALL.

`outbox-spec-purpose-stale` — `openspec/specs/outbox/spec.md:3-8` (named contract material) всё ещё описывает capability как «a command that scaffolds a conforming draft, and a check that names what a draft lacks», хотя после мерджа дельты в ней живут ещё send-транзакция и status-отчёт. Требования правильные, устарел только Purpose.
