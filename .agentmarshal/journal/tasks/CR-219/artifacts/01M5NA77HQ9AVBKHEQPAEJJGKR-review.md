## Findings

**OP-1 (blocking) — `openspec/specs/extension-stages/spec.md` is left asserting the behaviour this diff removes, and its spec directory is outside the contract's scope so no delta could be archived for it.** That capability's requirement "`stage run` invokes the declared stages of the base's shared extensions" states without qualification that "A `--phase pre-gate` invocation SHALL run each `[[stage]]` whose phase is `pre-gate-warn` or `pre-gate-stop`" and that "A manifest the base-tree reader refuses SHALL fail the command naming the extension and its tree source" (`openspec/specs/extension-stages/spec.md:30-52`), with the scenario "a manifest the base cannot parse fails the run naming the extension" promising it "fails naming the extension and its tree source, and no stage is planned" (`:74-78`). The diff's own `test_a_broken_extension_cannot_block_the_operational_change` asserts the opposite in exactly that situation — a malformed manifest at the base, exit 0, the operational line. The same capability's "`stage run` reads the switches from the base and reports a switched-off extension" (`:429-445`) is likewise no longer true on an operational pre-gate run: nothing is read from the base's file by `stage run` and no `<name>: switched off (<task>, <reason>)` result line prints, although the base may well hold an `off` entry (the shape `test_switching_an_extension_back_on_names_this_task` builds). The new `stage run` requirement was instead placed under `gate-lanes`, which the proposal lists as the only modified capability. `AGENTS.md:18-21` requires the contract's scope to name "the affected `openspec/specs/<capability>/` directory" for the archive, and the contract names only `openspec/specs/gate-lanes/` — so this needs a contract amendment adding `openspec/specs/extension-stages/` and a MODIFIED requirement there, not a change to the implementation. Until then the repository publishes two live requirements that contradict each other on the same command.

**OP-2 (advisory) — the new `gate-lanes` requirement claims more than the lane does: the contract-scope check neither runs nor is reported.** `openspec/specs/gate-lanes/spec.md:179-181` (and the identical delta at `openspec/changes/archive/2026-10-24-gate-operational-lane/specs/gate-lanes/spec.md:46-48`) says "every check that does not depend on a review SHALL run as on the diff lane". The scope check does not depend on a review, and the operational branch replaces the whole scope-through-implementers block (`src/agentmarshal/journal/gate.py:1327`), printing no scope line at all — not a PASS, not a NOT EXAMINED. The pinned transcript inside `test_the_operational_lane_admits_a_switches_only_candidate` confirms the silence. It is not merely unmet but unmeetable as written: the regular lane's scope check has no journal exemption (`gate.py:1556`, `outside = [path for path in changed if not scope_covers(effective, path)]`), so running it would refuse every operational candidate that adds its own session record, since the lane requires the scope to be exactly `[".agentmarshal/switches.toml"]`. `design.md` is accurate here ("In place of the regular lane's scope-through-implementers block"); the published requirement is the text that is wrong, and the transcript stays silent about a judgement the lane does make by construction — the same silence the codebase elsewhere refuses ("reported, neither refused nor silently skipped", `gate.py:1589`). The extension-removal check is silent on the lane for the same reason, which the design does acknowledge.

**OP-3 (advisory) — `docs/threat-model.md` still describes the operational lane as unimplemented.** Entry 5 reads "The operational lane — decided, not yet implemented — admits a diff touching only `.agentmarshal/switches.toml` and the task's own records, requires no review, and skips the extensions' `pre-gate` stages" (`docs/threat-model.md:443-452`); `design.md` quotes that very entry while implementing it. Entry 2 is also now partly stale: it says "No published statement covers a symlink … or at `.agentmarshal/switches.toml`" (`docs/threat-model.md:410-415`), which the new `gate-lanes` requirement does now cover ("a link or a non-blob at the file's path refuses as not a file"). `docs/threat-model.md` is outside the contract's scope and the Non-Goals point readers at it, so this is not something the task could have fixed — flagged so a published document is not left making a false statement about the shipped lane.
