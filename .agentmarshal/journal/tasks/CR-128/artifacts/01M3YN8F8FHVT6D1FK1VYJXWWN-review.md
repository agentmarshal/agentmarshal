Below are the findings.

`gate-inside-complete-not-always-after-merge` — `docs/adr/ADR-0013-extensions-stages-scopes-isolation-trust.md:34-36` states flatly that the gate runs "inside `complete` — already after the merge", and Decision 2 at line 47-49 builds a rule on it: "Inside `complete`, `pre-gate` extensions run as a warning only: the merge has already happened." `docs/self-hosting-workflow.md:49-51` says the opposite is equally permitted — "Completion may run before or after the implementation merges, as long as `--base` stays an ancestor of the candidate." So the premise is wrong for one of the two supported orderings, and the consequence is substantive, not cosmetic: in the complete-before-merge case a `pre-gate-stop` extension is silently downgraded to a warning on the reasoning that a merge has already happened when it has not. Criterion 4 asks specifically that the "where the gate runs" statement match the file it rests on; this one does not.

`adr0007-acceptance-extended-without-declared-revision` — `docs/adr/ADR-0013-…:64-66` offers "operator acceptance under ADR-0007" as a way to clear an extension pause, and `:182-183` offers it for an operational CR; the Consequences line at `:247` concedes the point — "Operator acceptance extends from review findings to extension pauses." But ADR-0007 D2 (`docs/adr/ADR-0007-operator-acceptance.md:56-58`) makes an acceptance valid only when "the latest review of that exact commit is non-approving", naming "every blocking finding that review raised — all of them, and nothing else", and D3 (`:89`) closes the enumeration: an acceptance "substitutes for the approving-verdict check and nothing else." An extension pause raises no review finding, and an operational CR has no review at all, so no acceptance record of the form ADR-0007 defines can cover either. ADR-0013 is therefore revising ADR-0007, not applying it — yet its header (`:11-14`) declares a partial revision of ADR-0010 only. Either the header should name ADR-0007 among the decisions it partly revisits, or the two clauses should stop invoking ADR-0007 by name.

`merge-authority-term-conflicts-with-overview` (advisory) — `docs/adr/ADR-0013-…:33-35` says "The merge itself is made not by the tool but by the provider and the merge authority; the gate runs in CI, in the merge authority before the merge". In this repository's published vocabulary the merge authority *is* the gate: `docs/overview.md:67-69` ("The **gate** — the merge authority — … it never performs the merge itself; the provider does"), `:132-133`, and the glossary at `:143-145` ("**Merge authority** — the gate *decides*; the provider *merges*"). Under that definition the ADR's sentence both attributes the merge to the merge authority, which overview explicitly denies, and makes "the gate runs … in the merge authority" circular. The looser sense ADR-0013 intends — the host wrapper that runs the gate at merge time, `am-merge` in `docs/self-hosting-workflow.md:38-41` — does appear once in `docs/github-enforcement.md:43`, so this is a term collision rather than a factual error; naming the host wrapper or the provider's merge step would remove it.
